# 见微 / OasisMind v0.1.0 技术总览

> 版本：v0.1.0  
> 分支：master（本 tag 对应 commit 见下文 `git rev-parse`）  
> 文档用途：面向开发者与 AI 助手的全景式技术说明，涵盖模块划分、核心亮点、实现难点、解决方案与模块间交互。

---

## 1. 项目定位与核心原则

**见微（OasisMind）** 是一个**单用户、本地优先**的智能知识管理与博客平台，定位是「以 Markdown 为原子、AI 为引擎的数字花园」。

核心原则：

- **Markdown 是事实源**：`content/`、`config/` 下的 Git 跟踪文件是持久真相源；SQLite（Prisma）只是查询与缓存层，可随时重建。
- **本地优先**：所有关键运行态都落在本机，不依赖外部 SaaS；可选的云端能力（搜索、视频字幕、Agent 平台）仅作为扩展。
- **AI 为引擎**：从博客写作、知识整理、网页/视频抓取、代码可视化到定时任务，全部通过 Agent 化能力驱动。
- **状态在内存、推拉结合、刷新不丢**：前端零真相，权威在服务端；管理页与会话页必须实时更新，禁止「刷新一下就好」。

## 4. 核心架构与产品亮点

### 4.1 L1–L5 已落地能力

- **L1 博客与知识库**：Markdown 文章 CRUD、编辑器、图片上传/粘贴、Command Palette、分类/标签/FTS 搜索。
- **L2 Agent 与 Chat**：Agent CRUD、Skill/Memory/Prompt/MCP 配置、ReAct + SSE 流式 Chat、`skill:*` 双路径、MCP 截断重连熔断、auto-compact。
- **L3 文件与任务**：File/GitRepo/Task/Log/Workspace CRUD、Task sync/Scheduler。
- **L4 触发器与审批**：Trigger/Approval 后端 + 前端页面、审批拦截、定时清理。
- **L5 搜索、鉴权、部署**：`search.global` + FTS5、可选 `AUTH_MODE=password`、Docker/CI、`db:backup`。

### 4.2 Swarm 三层 Agent 架构

| 层级 | tier | 权限 | 归属 Workspace |
|------|------|------|----------------|
| 超级 Agent | `super` | 近似用户全能（禁删自己、禁自降 tier） | KnowPilot Root（`isSystem`） |
| 管理 Agent | `manager` | 本 Workspace 内 CRUD，禁止出域 | 业务 Workspace（创建时默认附带） |
| 子 Agent | `sub` | 执行任务，只能 `report_back` / `notify_parent` | 由管理 Agent 或用户创建 |

- 权限硬拦截：`infra/swarmPermissionGuard.ts`
- Agent 创建工厂：`infra/agentFactory.ts`（模板化三 tier 默认提示词）
- 心跳自主运行：`infra/heartbeatEngine.ts`
- 任务统一调度：`infra/swarmOrchestrator.ts`

### 4.3 Chat 三层 Store + SSE 流式

前端 Chat 状态拆成三层，避免单文件臃肿与循环依赖：

1. `useSessionMessages`：消息列表、hydrate、版本切换、幂等 patch。
2. `useStreamLifecycle`：流式生命周期 reducer（idle/streaming/done/error 等相位）、commit/abort 不变量。
3. `useSessionComposeState`：输入框、附件、引用。

后端 `SessionStreamHub` 采用「内存热缓冲 + SQLite 事件日志」双写：低延迟推送走内存，断线续传 / 服务端重启恢复走数据库。

### 4.4 Markdown ↔ SQLite 双向同步

- `pnpm db:sync` 扫描 `content/`、`config/` 下的事实源文件，写入/更新 SQLite。
- 运行时 CRUD 先改文件，再投影到 DB；删除走 `guardedWatchDeleteBySlug` 5s 改名窗口保护。
- FTS5 索引随 syncer upsert/delete 同步维护。

### 4.5 异步任务与全局任务池

- `async_task_run`：纯工具型后台任务（无 LLM）。
- `spawn_subagent`：带 LLM 的子 Agent 任务。
- `infra/asyncJobOrchestrator.ts` 是后台任务并发容量的单一事实源：maxGlobal、maxPerSession、maxPerWorkspace、maxQueued、taskTimeoutMs 等。
- `waitForResult=true` 血缘槽位继承，避免父子死锁。

### 4.6 审批与断路器

- `Approval.decisionScope` + `lastNotifiedAt`：跨工具集的审批冷却与 gate 相交。
- 通用三态断路器：`closed → open → half-open`，拒绝非法转移；MCP 工具 open 期零真实连接，返回结构化错误喂回 LLM。

### 4.7 心跳决策层

`infra/heartbeatDecision.ts` 纯函数叶子：收集 signals → `buildHeartbeatDecision` → 只有 `bounded_delivery` / `repair` 才入池，其余写 Log；`wait_user_gate` 附具体 summary；quiet/monitor 用 skip 计数退避。

### 4.8 推送-拉取结合的 UI 实时性

- PUSH：写库瞬间通过 `uiStateNotify.ts` 推 SSE / BroadcastChannel。
- PULL：进页/刷新从 DB 再水合；管理页对 running/pending 态保留短 `refetchInterval` 兜底。
- 禁止把「刷新一下」当修复。

## 5. 关键技术难点与解决方案

### 5.1 Chat 并发队列：流式中发第二条消息不会自动 drain

**难点**：用户第一条消息正在流式回复时，第二条消息应进入队列；流式结束后应自动发出队列消息。早期实现会卡死，或需要用户再发第三条才触发。

**方案**：
- 前端 `useStreamLifecycle` reducer 严格管理相位：`done → idle` 只经 `commitStream`。
- 队列 drain 由 `useChatQueueDrain` 监听相位变化：检测到 `!isSessionStreaming && queue.length > 0` 时调用 `runConsumeJob`。
- 服务端 `SessionQueueItemService.consume()` 改为软认领（`{success, claimed}`），防止双跑。
- 通过测试 `chat-queue-real.spec.ts`、`chat-resume-mock.spec.ts`、`superiorQueueDrain.test.ts` 覆盖。

### 5.2 服务重启后僵尸任务不能自动续跑

**难点**：本地工具任务有副作用，盲目续跑可能重复执行（发两封邮件、写两份文件）。

**方案**：
- `recoverStaleAsyncJobs` 启动时把所有僵尸 running/queued Task 标 failed（文案「服务重启，任务中断」）。
- `reentrant`/`maxRetries`/`retryCount` 三列已从 schema 删除。
- 用户可手动 `retryAsyncJob`；paused 会话走 `chatSession.resume` 手动恢复。

### 5.3 子 Agent 结果重复投递

**难点**：父 Agent 同时通过 `invoke_api` 通用后门读子会话消息、又通过 `autoConsume` 注入 tool result，导致同一份子 Agent 结果双通道重复投喂。

**方案**：
- 彻底下线 `invoke_api` 工具及所有兼容代码。
- `agent_inspect` 不再返回任何会话消息内容，只返回元信息（id/title/status/messageCount）。
- 子 Agent 结果唯一通道 = `agent_report_back` → `autoConsume` 注入父会话，带 jobId 台账。
- `infra/agentMessageLedger.ts` 负责 delivered/consumed 对账与 reconciler。

### 5.4 流式响应中 assistant 消息版本切换闪烁

**难点**：重试/切换历史版本时，`pickFresherMessage` 用 `content.length` 判断新旧，导致切到短版本时被长版本覆盖回，界面闪烁。

**方案**：比较前先检查 `toolResults.versionMeta.activeIndex`；index 不同即为版本切换，直接取 incoming，不走 `content.length` 逻辑。

### 5.5 工具结果被整体 JSON.stringify 后截断

**难点**：`reactLoop.ts` 原实现把工具结果整体 `JSON.stringify` 后 `slice(0, 16000)`，导致 `content` 字段在 JSON 中间被砍，LLM 只看到残缺正文。

**方案**：新增 `truncateToolResultContent` helper，优先砍 `content/text/transcript/excerpt/html/markdown` 等长文本字段，保留元信息完整，并加截断标记。

### 5.6 QQ/IM 渠道消息乱码与重复发送

**难点**：NapCat 接收到的消息编码异常、Bot 重复发送同一回复的多个片段。

**方案**：
- QQ 渠道提示词强制「纯文本、无 Markdown」。
- 消息网关增加 `dedupeKey` 与发送状态机，防止同一 assistant 回复被拆成多条重复发送。
- `/new` 指令正确切换默认绑定 session，防止消息回旧上下文。
- `/stop`、`/force` 支持强制停止当前回复。

### 5.7 平台登录态捕获不可靠

**难点**：`platform_login` 一度靠 storageState 文件大小判断登录成功，误判设备 cookie 为登录态，导致窗口一开即关。

**方案**：
- 每平台配置 `loginCookieNames`，只检查登录后才出现的认证 cookie。
- 未检测到登录态时不落盘、不覆盖旧登录态。
- 强反爬平台抓取优先使用 Playwright `storageState`（完整浏览器态），回退 cookieJar。

### 5.8 Workspace 隔离与 content/ 污染

**难点**：Agent `write_file` 直接写到 `content/` 根目录，污染知识库；各 Agent 工作产物未隔离。

**方案**：
- `content/config/data` 三分法重构。
- `write_file` 默认落到当前 Agent 的 Workspace 目录（`workspaces/{workspaceId}/`），`content/` 开头才走知识库。
- `resolveWithinDir` 强制路径边界。

## 6. 模块间交互

### 6.1 典型用户请求：Web Chat 发消息

```
用户输入
  → ChatInput / useSessionComposeState
  → useChatEnqueue（本地 queue + 乐观 UI）
  → tRPC chat.message.create 写 DB
  → SessionStreamHub.pushExternalEvent("message_upserted")
  → SSE 推送到前端
  → useChatRunStream 启动 /chat SSE
  → agentStream.ts prepareMessage
  → reactLoop（ReAct 内核）
    → 调用 LLM
    → 工具调用 → executeNativeTool / executeMcpTool
    → 结果回注 → 继续 LLM
    → done → finalizeRun
  → SessionStreamHub 推送 token / done / tool 事件
  → 前端 reducer 更新消息
  → useChatQueueDrain 检测到 idle → 若 queue 有残留 → runConsumeJob
```

### 6.2 Agent 创建与 Swarm 任务

```
用户创建 Agent / spawn_subagent
  → agentFactory.createAgentForTier(tier)
    → 读模板 config/agents/_templates/{super,manager,sub}.md
    → 缺省回退 shared 常量
  → Agent 写入 config/agents/{id}.md + DB
  → sync 服务感知文件变更（可选）

管理 Agent 派发子任务
  → swarmOrchestrator.dispatch(taskSpec)
  → swarmPermissionGuard 校验 tier / depth / 跨 Workspace
  → asyncJobOrchestrator 准入（global/session/workspace）
  → queued / started
  → prepareAgentRun / reactLoop
  → 子 Agent 完成后 agent_report_back
  → agentMessageLedger 对账
  → autoConsume 注入父会话异步结果队列
```

### 6.3 后台 Task 生命周期

```
TriggerEngine / HeartbeatEngine / 用户调用 async_task_run
  → asyncJobOrchestrator.enqueue(taskSpec)
  → 准入判定（global/session/workspace/maxQueued）
  → queued 状态落 DB（reason/position）
  → 有槽时 claimTaskRun
  → TaskService.run(task)
  → 执行步骤（native 工具 / subagent）
  → success/failed
  → uiStateNotify 推送 task_updated / run_updated
  → /runs /tasks 管理页自动刷新
```

### 6.4 Markdown 同步与 DB 投影

```
文件系统（content/config）
  ←→ sync-free-keys/sync-agents/sync-skills/sync-posts/...
    ←→ Prisma CRUD
      ←→ tRPC routers
        ←→ Next.js 前端

运行时写文件
  → FileSyncService 先写文件
  → 成功后 upsert DB
  → 失败时 guarded compensation
```

### 6.5 前后端实时通道

- **tRPC**：请求/响应 + React Query 缓存失效。
- **SSE**：`/chat` 端点单向流式，事件类型包括 `token`、`tool_call`、`tool_result`、`done`、`error`、`abort`、`message_upserted`。
- **BroadcastChannel**：跨浏览器标签页同步 UI 状态（如 session 切换）。
- **`uiStateNotify.ts`**：服务端统一 PUSH 入口，把异步事件转成 SSE / hub 内存 / BroadcastChannel。

## 7. 版本与分支约定

### 7.1 当前约定（v0.1.0）

- **主开发分支**：`master`，所有新功能、修复继续往这里合。
- **发布方式**：在 `master` 的某个稳定 commit 上打 tag，例如 `v0.1.0`。
- **GitHub Release**：可选，把 tag 推到 remote 后在 GitHub 上写 Release Note。
- **不维护 release 分支**：单人项目无需同时维护多个版本，徒增复杂度。
- **语义化版本**：`MAJOR.MINOR.PATCH`
  - MAJOR：破坏性重构或 1.0 正式发布。
  - MINOR：新功能集合（如 v0.2.0 加移动端、v0.3.0 加协作）。
  - PATCH：bugfix（v0.1.1、v0.1.2）。

### 7.2 v0.1.0 范围

v0.1.0 是当前 L1–L5 全部落地后的第一个对外 tag，包含：

- 完整博客与知识库。
- Agent/Swarm/Chat 运行态。
- Task/Trigger/Approval 工作流。
- FTS 全局搜索、可选鉴权、Docker/CI。
- QQ/IM 消息网关（NapCat 多开自动端口分配）。
- 语音输入/输出（浏览器原生）、视频转文字、多平台登录态捕获。
- content/config/data 三分法重构。

### 7.3 后续开发流程

1. 继续在 `master` 开发。
2. 每次完成一个可交付主题后，`git commit`。
3. 累积到下一个里程碑时，在 `master` 上打下一个 tag（如 `v0.2.0`）。
4. 如需对外发布，推送 tag 并创建 GitHub Release。

## 9. 已移除的旧设计

| 旧设计 | 移除原因 | 替代方案 |
|--------|----------|----------|
| `invoke_api` 工具 | 万能后门导致子 Agent 隔离失效、双通道重复投喂 | 闭工具集 + `agent_report_back` 唯一交付 |
| `async_task_wait` 工具 | 结果全文交付通道不统一，撞车面复杂 | `Task.delivered` 原子 claim |
| Task `reentrant`/`maxRetries`/`retryCount` | 服务重启自动续跑会导致副作用重复 | 僵尸任务标 failed，用户手动 retry |
| content/ 混合配置与运行时目录 | 污染知识库事实源 | content/config/data 三分法 |
| `agent.apiKey` 字段 | 死字段 | credentialVault 统一管理 |

## 10. 已知的边界与后续方向

### 10.1 边界

- 当前默认 `AUTH_MODE=none`，暴露公网必须启用鉴权 + 反向代理 + 限流。
- SQLite 是本地单用户方案；多用户/高并发需要切 PostgreSQL。
- 运行中的 Agent 任务执行体随服务端进程重启而丢失（设计如此，不自动续跑）。
- QQ/IM 渠道目前按单账号 Bot 模式优化；多 Bot 同时在线需要 NapCat 多开 + 端口分配（已有 `ONEBOT_HTTP_URL` 自动分配）。

### 10.2 后续方向（非 v0.1.0 范围）

- 移动端适配 / PWA。
- 更完善的权限模型（多用户、RBAC）。
- PostgreSQL 生产部署。
- Agent 长期记忆的外部向量存储（Milvus/pgvector）。
- 跨机器部署与云端同步。
